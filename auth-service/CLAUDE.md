# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`auth-service`: Spring Boot 4.1.2 / Java 21 REST service for member registration, backed by MongoDB (`membership` database). Base package: `kitchen.sink.demo`. The service was renamed from `demo` to `auth-service` (Maven artifact, `spring.application.name`, jar name and docs); the Java package and the checkout directory keep the old `demo` name. Build tool is Maven (use the `./mvnw` wrapper).

## Commands

```bash
./mvnw spring-boot:run                      # run the app (needs MongoDB at mongodb://localhost:27017)
./mvnw clean package                        # build the jar into target/
./mvnw test                                 # run all tests
./mvnw test -Dtest=DemoApplicationTests     # run one test class
./mvnw test -Dtest=ClassName#methodName     # run one test method
```

No linter or formatter is configured. Tests live in `src/test/java` and mirror the main packages: `@WebMvcTest` controller tests (with `GlobalExceptionHandler` in the `@ContextConfiguration`) and Mockito unit tests for `RegistrationServiceImpl`. `AuthApplicationTests` and `TracePropagationTest` are `@SpringBootTest`s that need no MongoDB or Valkey (`mongock.enabled=false`, `ProxyManager` mocked with `@MockitoBean`), so they run in CI. `MongoAuthorizationGrantStoreTest`, `SessionRepositoryTest` and `MigrationsTest` need a real MongoDB (atomic updates, validators, indexes), so they are tagged `integration` and skipped by default; run them with `./mvnw test -DexcludedTestGroups=none` against a MongoDB at localhost:27017.

JaCoCo is wired into the build and its report is generated in the `test` phase (`target/site/jacoco`), excluding `AuthApplication` and `*MapperImpl`. Surefire's `argLine` is set to `@{argLine} -javaagent:${org.mockito:mockito-core:jar} -Xshare:off` so JaCoCo and the Mockito agent work together, so keep it when editing the build.

## Architecture

Layered structure: `controller` → `service` (interface in `service/`, implementation in `service/impl/`) → `repository` (Spring Data `MongoRepository`) → `entity`. Controllers are package-private methods on `@RestController` classes and use constructor injection.

Endpoints:
- `POST /register` (`RegistrationController`) takes a `@Valid` `RegistrationRequest` (first and last name each max 25 and no digits, valid email, 10-12 digit phone) and returns 200 with a `RegistrationResponse`, or 409/500/503 if the member could not be created (see below).
- **Member sync to member-service (REST, OpenFeign):** `RegistrationServiceImpl` saves the member and then calls member-service's `POST /members` through the OpenFeign client `client/MemberServiceClient` (`@FeignClient`, `@EnableFeignClients` on `AuthApplication`; base URL `app.member-service.url` / `MEMBER_SERVICE_URL`, default `http://localhost:8081`; connect 2 s / read 3 s under `spring.cloud.openfeign.client.config.member-service`) with `CreateMemberRequest` (`email`, `phoneNo`, `firstName`, `lastName`; **never the password or its hash**). The call is synchronous, inside the registration transaction. **If it fails the registration is undone**: the saved member is deleted (explicitly, since a standalone MongoDB has no transaction to roll back) and `MemberServiceException(status)` is thrown, which `GlobalExceptionHandler` answers in the usual `ErrorResponse` body: member-service 503 or no answer (connection refused, timeout) -> 503 `Registration is temporarily unavailable, please try again later`; member-service 409 -> 409 `Member Already Exist`; anything else (500 and so on) -> 500 `Something went wrong, please try again later`. The cause is only logged, never shown. Known gap: there is no retry, and if the later commit fails after a successful call, member-service keeps a member auth-service does not have. There is no in-process event any more. Spring Cloud `2026.0.0` (`spring-cloud.version` in the pom) targets Boot 4.2.x and this service is on 4.1.2, so `spring.cloud.compatibility-verifier.enabled=false` is set; remove it when Boot moves to 4.2. member-service's endpoint is open for now (no token is sent); **future scope: this call must carry a service-client token** (client-credentials grant, for example through a Feign `RequestInterceptor`) so nobody can create a member without registering (see the future-scope note on `MemberController#createMember` in `../member-service`). Members registered before this feature are not backfilled; keep `CreateMemberRequest` in sync with member-service's. Kafka is no longer used.
- The member read APIs (`GET /members`, `GET /members/{email}`) were removed from this service; `../member-service` serves them (it keeps its own `member` collection, filled by the call above) and trusts this service's access tokens (see its `CLAUDE.md`).

### Authentication (passwords, sessions, tokens)

- **Hosted pages:** `PageController` serves `GET /login` and `GET /register` (Thymeleaf templates `templates/login.html` and `register.html`; static `static/pages/register.js` and `auth.css`, no inline scripts: `SecurityConfig` sends a CSP with `script-src 'self'` and no `form-action`, because the login 302 goes to the client's redirect URI). The login form is a plain browser POST to `POST /login` (form-encoded `email`, `password`, `request_id`), not a `fetch`, so the browser can follow the 302 with the code; a failure is a 303 back to `/login?request_id=...&error=invalid|invalid_input|expired`. The register page calls `POST /register` with `fetch`. `app.oauth.login-url` now defaults to this service's `/login` (override with `OAUTH_LOGIN_URL` to keep the Next.js front end).

Responsibilities are split by interface (SOLID): `AuthService` proves identity (the password), `SessionService` only changes sessions (start, rotate the refresh token hash, revoke) and never creates or checks tokens, the grant handlers create their own tokens (`AuthorizationCodeGrantHandler` for the code exchange, `RefreshTokenGrantHandler` for a refresh) and `AccessTokenIssuer` is the token contract (`JwtService` is the RS256 implementation). Services depend on these interfaces, never on the concrete classes. Configuration is split the same way: `SecurityConfig` (filter chain), `JwtConfig` (keys, encoder, decoder) and `PasswordEncoderConfig`.

- `SecurityConfig` is a stateless bearer-JWT filter chain (no HTTP session, CSRF off). Public: `POST /register`, `GET /oauth2/authorize`, `GET /login`, `GET /register`, `POST /login`, `POST /oauth2/token`, `/actuator/health`, Swagger/`/openapi.yaml`. Everything else needs `Authorization: Bearer <jwt>`; 401/403 are written as `ErrorResponse` JSON by `security/RestAuthenticationHandlers`.
- Registration requires a `password` following the NIST SP 800-63B / OWASP guidelines: `security/PasswordPolicy` enforces 15-64 characters (fixed constants in `PasswordPolicy`, not configuration, counted in code points), the registration and login DTOs check the same 15 <= size <= 64 in UTF-16 units (so an emoji counts twice there); all characters allowed, no trimming/truncating, no Unicode normalization (the same visible password typed in two encodings is two passwords), no composition rules. Hashing is SHA-256, Base64, then BCrypt (`Sha256BcryptPasswordEncoder`, so nothing past BCrypt's 72 bytes is dropped); the stored value is a bare `$2a$...` hash with no algorithm label and no delegating encoder. Hashes are not migrated between schemes: on a change or a move to a new portal, users reset their password. Hashes stored by the earlier `{sha256-bcrypt}`-prefixed or plain-BCrypt scheme no longer verify. Login bodies outside 15-64 characters are a 400 (so members whose password predates the 15 minimum cannot log in until it is reset); a password over 64 code points but within the DTO bound (only possible with characters outside the basic plane) gets the normal 401 after a dummy comparison. Only `Member.passwordHash` (`password_hash`) is stored. Members created before passwords existed have none and cannot log in. `RegistrationRequest`, `LoginRequest` and `TokenResponse` redact secrets in `toString()`; keep that.
- **OAuth 2.1 authorization code + PKCE (the only way to get tokens):** this service is the authorization server for registered **public** clients (`OAuthClient`, collection `oauth_client`: `clientId`, `name`, `aud` (list of audiences for its tokens), exact-match `redirectUris`, `active`; no secret, no admin API yet, so insert documents by hand). the flow follows RFC 6749 section 4.1 + RFC 7636 (OAuth 2.1): the client sends the browser to `GET /oauth2/authorize` (public; `response_type=code`, `client_id`, `redirect_uri`, `code_challenge` (43-char base64url), `code_challenge_method=S256` only, no `plain`; optional `state` (printable ASCII, max 512; stored on the grant and echoed unchanged in every redirect to the client, success and error, together with `iss` = `app.security.jwt.issuer` per RFC 9207; both built by `service/impl/ClientRedirects`; the login-page redirect never carries them)). `AuthorizationCodeService.authorize` stores an `AuthorizationGrant` (collection `oauth_authorization`) under a random `requestId` and answers 302 to `app.oauth.login-url` (`OAUTH_LOGIN_URL`, the front-end login page) + `?request_id=`. An unknown client or a redirect URI that is not an exact match answers 400 and is never redirected to; a bad `response_type`/`code_challenge`/method is a 302 to the redirect URI with `error`. The login page posts the form to `POST /login` with only `email`, `password` and `request_id` (an unknown/expired request is refused before the member is looked up, as a 303 back to the login page with `error=expired`); there is no second factor: once the password is accepted, `complete(requestId, userId)` turns the open grant (the member is set on it only now) into a one-time authorization code (60 s; only its SHA-256 is stored; `requestId` is unset) and `POST /login` answers **302** with `Location` = the registered redirect URI + `?code=` (+ `state`, `iss`), no body (the service still builds an `AuthorizationCodeResponse(redirectTo, expiresIn)` internally); so the login page must submit login as a browser navigation, a cross-origin fetch cannot follow that redirect. A request that is unknown, expired or already issued is a 400 `InvalidAuthorizationRequestException`. `POST /oauth2/token` (public, JSON body `TokenRequest` with camelCase fields, always `grantType` + `clientId`; not the form-encoded body of RFC 6749, a deliberate deviation so every endpoint takes JSON) is a strategy + factory: `TokenExchangeServiceImpl` asks `service/grant/GrantHandlerFactory` (built from every `GrantHandler` bean, keyed by `grantType()`; duplicates fail at startup, an unknown type is a 400) for the handler and delegates. **A new grant type is a new `GrantHandler` `@Service`, nothing else changes.** Each handler checks its own parameters (missing ones: 400 `InvalidGrantException`). `AuthorizationCodeGrantHandler` (`authorization_code`: `code`, `codeVerifier`; no `redirectUri`, the code is bound to the one stored on the grant) marks the code `USED` atomically first (`consumeCode`; the grant keeps `status` REQUESTED, CODE_ISSUED, USED and, after the exchange, the `sessionId` (a record only: a replay of a used code is just a 400 and revokes nothing), until the 60 s TTL removes the document), then checks the client and `Pkce.matches` (the redirect URI is re-checked only against the client's registered list), then creates the tokens itself (private `issueTokens`: it picks the session id, creates the access JWT and the refresh secret) and only then calls `SessionService.start(sessionId, userId, clientId, refreshTokenHash, ip)`, which just saves the session (the hash of the refresh secret, never the tokens); its `handle` is `@Transactional(noRollbackFor = InvalidGrantException.class)` a rollback would restore the burnt code and allow verifier guessing. `RefreshTokenGrantHandler` (`refresh_token`: `refreshToken`) does the whole refresh itself in `handle` (active registered client, rate limit, `SessionService.rotateRefreshToken` for the rotation and replay revocation, then it creates the new tokens); a refused token becomes `InvalidGrantException` (400). The refresh token is bound to the client that got it (`Session.clientId`, set by `SessionService.start`; `rotateRefreshToken` matches it atomically, so a refresh by another client is refused and, like a replay, revokes the session). Every refusal is the same 400 per message. Token JSON keeps the existing camelCase `TokenResponse`. The `refresh_token` grant on `/oauth2/token` is the only refresh endpoint (there is no `/auth/refresh`). There are no scopes. Migrations `V009` and `V010` create the indexes (unique `clientId`, unique sparse `requestId`/`codeHash`, TTL on `expiresAt`; `V011` dropped the grant's `challengeId` index). MFA (email code after the password) was removed: `V012` dropped the `mfa.challengeId` index and unset `member.mfa`; Kafka notifications, the later member-registered Kafka event (now a REST call, see above) and email verification were removed too (`V013` unset `verified`, `email_verification_hash` and `email_verification_expires_at`; members can log in right after registering); `V007`/`V008` are kept because applied change units are never edited.
- A `Session` is created by the token exchange (collection `session`, TTL index on `expiresAt`) and the exchange returns an RS256 access JWT (15 min; `aud`=the `aud` list of the `oauth_client` the session was issued to (read when the token is issued, nothing hardcoded; `azp`=that client's `clientId`; `name` is only a display name; migration `V016` backfilled `aud=[name]` on clients that had none; **no token is ever issued without a session id and a registered client**: `AuthorizationCodeGrantHandler` refuses an unknown client before issuing (a client without an `aud` still gets tokens, but the decoder rejects them), `SessionServiceImpl.start` refuses a blank session id or client, and `refresh` refuses an unknown or missing client before rotating the refresh token, so a session from before the client binding must log in again; the decoder rejects any token whose `aud` does not contain `app.security.jwt.audience` (`JWT_AUDIENCE`, default `auth-service`), so every client's `aud` list must include it); `sub`=the member's email (sessions and grants are keyed by `userId`, the member's Mongo `_id`; refresh and the code exchange load the member by it), `sid`=session id, `ip`=the client IP address the session was started from (a claim only: requests are not compared against it; refresh reuses the IP stored on the session); the user agent is not stored or sent anywhere; checked statelessly, so a logged-out session's access token lives until it expires; the token's lifetime is capped at the session's `expiresAt`, see `AccessTokenIssuer`) plus an opaque refresh token (7 days): a random 256-bit secret that names nothing (no session id inside), so the session is found by the SHA-256 of the token (`Session.refreshTokenHash`, unique index `uk_session_refresh_token_hash`; only the hash is stored; `V015`; the rotation replaces the hash and keeps no previous one, and `V015` also created `idx_session_previous_refresh_token_hash`, now unused and left in place because applied change units are never edited). Refresh tokens issued in the old `<sessionId>.<secret>` format no longer work, those users log in again.
- A refresh (`refresh_token` grant) is run by `RefreshTokenGrantHandler.handle`, which has `SessionService.rotateRefreshToken` rotate the secret atomically (`SessionRepositoryImpl.rotateRefreshToken`, a single `findAndModify`) and then creates the tokens. The presented token is looked up by its hash as the session's current one and the issuing client; a match gets the new hash, anything else (unknown, already replaced, another client's) is a 400 `InvalidGrantException` with no session revoked. `POST /auth/logout` takes the access token from the `Authorization: Bearer` header; `AuthService.logout` decodes it and `SessionService.revoke` deletes only that token's session (the caller's own). Sessions have no `revokedAt`: rotation does not check `expiresAt` or revocation, because the TTL index (`expiresAt`, kept for the TTL and the token cap) and the delete at logout remove those sessions (the TTL monitor can lag about a minute). There is no replay detection: a replaced token is just a 400.
- Config is `app.security.jwt.*` (`JwtProperties`). Access tokens are signed RS256 with the PEM pair whose **contents** are in the environment variables `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY` (no defaults, not file paths; a literal `\n` stands for a line break); `config/JwtKeys` parses them (PKCS#8 private, X.509 public, >= 2048 bits, must match) and the app will not start without a valid pair. Tests get a throwaway pair from `src/test/resources/jwt-test.properties` via `@TestPropertySource(locations = "classpath:jwt-test.properties")` (the PEM files in `src/test/resources/test-keys` are the same keys). `@WebMvcTest` controller tests use `@AutoConfigureMockMvc(addFilters = false)`; `SecurityConfigTest` exercises the real filter chain against the test-only `ProtectedProbeController` (`/probe`), since this service has no other protected GET endpoint. The access tokens it issues are also verified by `../member-service`, so every client's `aud` list must include that service's audience (default `member-service`) as well as this one.
- `RateLimitFilter` is ordered before Spring Security (-101) so login guessing is throttled per IP. Limits are fixed constants in `RateLimitConfig`, not configuration (bucket4j in Valkey, 60 s window): 40/IP for everything except `GET /oauth2/authorize`, which has its own bucket of 60/IP (constant `RateLimitConfig.AUTHORIZE_MAX_REQUESTS`; a second filter at -102, the global one skips that path). There is no per-client or per-session limit on `POST /oauth2/token`, only the per-IP ones. The filters answer 429 over the limit and 503 if Valkey is down (fail closed).
- **Password check:** `AuthServiceImpl.login` authenticates through Spring Security: an `AuthenticationManager` (`config/AuthenticationConfig`: `ProviderManager` + `DaoAuthenticationProvider` with `MemberUserDetailsService` and the project's `Sha256BcryptPasswordEncoder`). `MemberUserDetailsService` loads the member by normalized email and returns a `MemberPrincipal` (wraps the `Member`; the account checks keep their default of true). A member without a password is treated as unknown. Every failure (unknown email, wrong/over-long password, no password) is the same 401 `Invalid email or password`; an over-long password is refused before hashing, and for an unknown email the provider compares against a dummy hash, so timing does not reveal whether an email is registered.

### API docs and actuator

- `config/SwaggerConfig` defines the springdoc `OpenAPI` bean (springdoc-openapi-starter-webmvc-ui), so Swagger UI is served by springdoc, but `springdoc.swagger-ui.url=/openapi.yaml` makes it display the hand-written spec below rather than the one generated from the code.
- `src/main/resources/static/openapi.yaml` is a hand-written OpenAPI 3.0.3 spec covering `/register`, `/oauth2/*` and `/auth/*`. Update it when endpoints or DTOs change.
- `docs/oauth2-pkce-flow.mmd` (raw Mermaid source) and `docs/oauth2-pkce-flow.md` (same diagram in a fenced block, plus the rules the flow enforces) show the OAuth 2.1 PKCE flow as a sequence diagram: User (actor), Client App and auth-service. Only services are participants (no databases or Valkey). Login (password) is shown only as a big block saying the user starts authentication with password; then the code redirect and the token exchange. The diagram covers only the OAuth 2.1 PKCE flow (no member retrieval, refresh or logout). Update both files together when the flow changes. Mermaid pitfalls: `;` splits statements (write `#59;`), `&`, `<` and `>` need `#38;`, `#lt;`, `#gt;`, and the `.mmd` file must have no code fences.
  - Authorize failure in the diagram: unknown client or redirect URI mismatch is a 400 that is never redirected to the client; other bad parameters are a 302 to the redirect URI with `error`.
- `docs/login-flow.mmd` and `docs/login-flow.md` show the login flow (User and auth-service, password, ending in the authorization code redirect). Keep it in sync with the Authentication section above and follow the same Mermaid pitfalls.
- `docs/registration-flow.*` (User, auth-service and member-service, with the member-service call) and `docs/database-schema.*` (Mongo collections as an ER diagram, with indexes and other stores in `docs/database-schema-notes.md`) are further Mermaid docs. Keep the schema in sync with the entities and migrations, and the registration flow with `RegistrationServiceImpl`, `MemberServiceClient` and member-service's `MemberController#createMember`.
- `docs/notification-service-database-schema.mmd` (ER diagram of the notification-service `notification_log` collection) and `docs/notification-service-database-schema-notes.md` (indexes and what is stored) describe the sibling service's database. Keep them in sync with `../notification-service` `model/NotificationLog`.
- Spring Boot Actuator is enabled with health details always shown (`management.endpoint.health.show-details`).

DTOs live in `dto/request` and `dto/response` (records, constructed by positional args). MapStruct and its `annotationProcessorPaths` are still configured in `pom.xml` but nothing uses them since `MemberMapper` moved to member-service. The compiler plugin's `annotationProcessorPaths` order for Lombok, `lombok-mapstruct-binding` and MapStruct in `pom.xml` is required for both to work, so keep it when editing the build.

**Logging:** every class that decides something has an SLF4J `log`. INFO for state changes (registered, password accepted, authorization request/code, session start/rotate/revoke), WARN for refusals and security events (failed login, bad/replayed token, refused refresh, rate limit), DEBUG for request entry and repository outcomes, ERROR for unexpected failures (with the exception). Log ids (`userId`, `clientId`, session id, IP), never secrets or PII: no passwords, codes, tokens, verifier, request id, or email addresses.

Errors are all handled centrally in `exception/GlobalExceptionHandler`, which maps exceptions to an `ErrorResponse` (status, message, timestamp):
- Client-facing domain exceptions extend `RuntimeException` and each has an explicit `@ExceptionHandler` in `GlobalExceptionHandler`: `AuthenticationFailedException` 401, `ForbiddenException` 403, and `InvalidPasswordException`, `InvalidGrantException` and `InvalidAuthorizationRequestException` 400 (shared `refuse` helper). **A new domain exception needs its own handler method (or an entry in an existing one).** Its message must be safe to show to clients.
- `DuplicateKeyException` → 409
- `MemberServiceException` (member-service call failed, registration undone) → its own status: 503, 500 or 409
- `ConstraintViolationException`, `MethodArgumentNotValidException`, `HandlerMethodValidationException` and unreadable/mistyped requests → 400

### Data integrity is enforced in three layers

Keep these in sync when changing the `Member` model:
1. **Bean Validation** annotations on the `Member` entity. `config/MongoValidationConfig` registers a `ValidatingEntityCallback`, so validation runs on every repository save, not only at the controller boundary.
2. **Mongock migrations** in `migration/` (scanned via `mongock.migration-scan-package` in `application.yaml`, enabled by `@EnableMongock` on `AuthApplication`). `V001` creates the unique index `uk_member_email` on `email`. `V002` adds a `$jsonSchema` validator capping `name` at 25 characters (`V014` moved this to `first_name`/`last_name`). Schema or index changes go in a new `@ChangeUnit` with the next `order` value and a `@RollbackExecution`. Do not edit applied change units.
3. The unique email index surfaces as `DuplicateKeyException`, which becomes the 409 response. Registration relies on this rather than a pre-check.

### Transactions

`config/MongoConfig` (the single class for all Mongo wiring: client timeouts/tracing, mapping, transactions) registers a `MongoTransactionManager` (majority read/write concern, 5 s commit limit) so `@Transactional` works. MongoDB transactions need a replica set: production has one; a standalone local `mongod` rejects them, so on one run with `MONGO_TRANSACTIONS_ENABLED=false` (the annotations are then ignored).

**A method that burns a one-time secret and then throws must be `@Transactional(noRollbackFor = ...)` for that exception** (`AuthorizationCodeGrantHandler.handle` with `InvalidGrantException`). Plain `@Transactional` rolls the burnt code back together with the exception, which would allow verifier guessing. Also keep out of transactions anything that retries after a duplicate-key error (the member-id retry in registration): that error aborts the whole Mongo transaction.

### Mongo mapping details

- `config/MongoConnectionCheck` pings MongoDB when the context starts and throws if it is unreachable, so the service refuses to start without a database (bounded by `app.mongo.server-selection-timeout-ms`).
- `config/MongoConfig` also removes the `_class` type field from stored documents by setting the type mapper to `DefaultMongoTypeMapper(null)`.
- `Member` maps `phoneNo` to the Mongo field `phone_number`, `firstName`/`lastName` to `first_name`/`last_name`. There is no business `memberId` (removed by `V014`, which also re-keyed sessions to `userId`); `Member.id` (the Mongo ObjectId) is the internal key and the email is the public one. `MemberIdGenerator` stays only because the applied `V004` uses it. The collection is named `member`.

## Claude Code skills

`.claude/skills/spring-boot-junit-testing/` holds a project skill for writing JUnit 5 tests for Spring Boot. It checks existing tests first, picks the lightest test type (unit, `@WebMvcTest`, `@DataMongoTest`, `@SpringBootTest`), prioritizes by criticality (`@Tag("critical")`), and then writes and runs the tests.
