# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`notification-service`: Spring Boot 4.1.2 / Java 21 Kafka consumer (base package `com.demo.notification`, Maven via `./mvnw`). It delivers notifications and tracks every attempt in MongoDB (`notification_service` database). It sends email notifications from **templates** (`MFA_CODE`, `OTP`, `FORGOT_PASSWORD`, `VERIFY_EMAIL`, `ACCOUNT_BLOCKED`; the last two are email-only) chosen by the producer, and email sending is a **mock that logs the whole email including the code**. It is meant to be **extended to integrate with an email service/provider that actually sends the emails**; do that by adding an `EmailSender` implementation, not by changing the consumer flow.

**There is no REST API and there must never be one for sending.** Kafka is the only entry point. Do not add the web starter or controllers.

Producer: the auth-service in `../demo` (`KafkaNotificationPublisher`). The contract is `docs/event-payload-design.md`; `docs/recommendation.md` holds the production recommendations.

## Commands

```bash
./mvnw spring-boot:run     # needs Kafka (localhost:9092) and MongoDB (localhost:27017); `docker compose up -d` starts both
./mvnw test                # all tests
./mvnw test -Dtest=NotificationServiceTest#sendsEmailAndMarksSent
```

`NotificationServiceApplicationTests` turns off listener auto-start and topic creation so the context loads without Kafka. `DeadLetterIntegrationTest` uses `@EmbeddedKafka` and a mocked repository; it proves 4 send attempts (1 + 3 retries) and then a record on the DLT.

## Architecture

`listener/NotificationListener` (`@KafkaListener`, String payload) → `service/NotificationService.process` → `NotificationEventParser` (parse + validate) → `DeliveryChannel` (`EmailChannel` = `TemplateRenderer` + `EmailSender`) → `repository/NotificationLogRepository` (Mongo). `listener/DeadLetterRecoverer` (wired into `KafkaConfig`'s error handler) calls `FailureRecorder` to write the FAILED/REJECTED trace, then publishes to the DLT.

Packages: `service/` holds only the service contracts (`NotificationService`, `NotificationEventParser`, `FailureRecorder`, `TemplateRenderer`, `DeliveryChannel`, `EmailSender`); every implementation is in `service/impl/` (`*Impl`, `EmailChannel`, `MockEmailSender`). Template building blocks (`NotificationTemplate`, `DataField`) are in `template/`, and the outgoing value objects (`EmailMessage`) in `message/`. A real provider is a new class in `service/impl/` implementing `EmailSender`.

SOLID notes: `NotificationService` only orchestrates (SRP) and knows channels only through the `DeliveryChannel` interface, so a new channel (push, WhatsApp) is a new `@Component` implementing it plus its templates, with no edit to the flow (OCP/DIP). The sender interface (`EmailSender`) is small (ISP), and every provider implementation must honour the `NotificationSendException(retryable)` contract (LSP).

- `NotificationService.process`: parse JSON (Jackson 3, `tools.jackson`), Bean Validation, check `eventType`, schema major version `1.x`, channel `EMAIL` (the only one); skip a duplicate `eventId` unless it is still `PENDING`; mark `EXPIRED` past `expiresAt` (checked on every attempt); record the attempt; send; mark `SENT`.
- `model/NotificationLog`: `_id` is generated by Mongo; the producer's `eventId` is a plain field and a unique partial index on (`source`, `eventId`) makes redelivery idempotent per producer (a duplicate insert race surfaces as `DuplicateKeyException` and the event is skipped). A TTL index on `createdAt` deletes records after `app.log.retention` (default 24h), which is also the de-duplication window; both indexes come from annotations via `spring.data.mongodb.auto-index-creation=true`. `correlationId` is deliberately not stored. It stores the masked address, status (`PENDING`/`SENT`/`FAILED`/`EXPIRED`/`REJECTED`), attempts, failure reason (validation messages as written, which never contain values; any other error reduced to the exception class name), the Kafka topic/partition/offset of the dead-lettered record, , `requestedAt`/`createdAt`/`sentAt`/`updatedAt`. **Never store the MFA code or any event `data`.**
- `EmailSender` is the delivery boundary. `MockEmailSender` (`app.mail.provider=mock`, the default) logs the email. A real implementation throws `NotificationSendException(retryable)`; `retryable=false` is turned into an `InvalidNotificationException` (straight to the DLT).
- Templates: `TemplateRenderer` (impl `TemplateRendererImpl`) is the registry keyed by `notificationType` + `channel` (`EMAIL` only today). Each `NotificationTemplate` has `DataField` rules and texts from `src/main/resources/templates/<TYPE>/EMAIL/{subject.txt,body.txt,body.html}` (`{{placeholders}}`; HTML body escaped; single-pass substitution). `renderEmail` produces an `EmailMessage`. `NotificationEventParser.parse` checks the channel (EMAIL needs `recipient.email`) and calls `renderer.validate`, so an unknown type/channel or bad `data` goes to the DLT before any record exists. Validation messages must not include values.
- `EmailSender` is the delivery boundary (`MockEmailSender` logs the whole message, code included; `app.mail.provider`). It throws `NotificationSendException(retryable)`. The tracking record stores the masked address (`a***@example.com`).
- `config/KafkaConfig`: creates the `notification.high-priority` and `.DLT` topics (same partition count) and the `DefaultErrorHandler`: exponential backoff (`app.retry.max-retries`=3 retries, `initial-interval`, `multiplier`), `InvalidNotificationException` is not retried, and the recoverer calls `NotificationService.recordFailure` (existing PENDING record -> `FAILED`; an event that never got a record -> new `REJECTED` record; a malformed one has no `source`/`eventId`, only the reason and Kafka coordinates; a terminal record such as `SENT` is never overwritten) then publishes to the DLT. Spring Boot applies this handler to the listener container automatically. Retries block the consumer thread; switch to non-blocking retry topics before production.
- Tracing: `spring-boot-starter-opentelemetry` + `spring.kafka.listener.observation-enabled`: each consumed record continues the producer's trace from its W3C `traceparent` header, and `traceId`/`spanId` are in the log MDC (log pattern `[traceId=… spanId=…]`, set via `logging.pattern.correlation`). Spans go to `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (default `http://localhost:4318/v1/traces`); sampling `TRACING_SAMPLING_PROBABILITY` (default 1.0). `TraceContextIntegrationTest` covers it.
- Consumer group `notification-service`, manual offsets (`ack-mode: record`), String key/value serializers.

## Rules

- Never log event `data` or the code outside `MockEmailSender` (`NotificationEvent.toString()` deliberately omits it). The mock's logging of the code is for local development only.
- New template (accepted automatically once registered; `NotificationEventParser` reads the type list from `TemplateRenderer`): files under `templates/<TYPE>/EMAIL`, register it with its `DataField`s in `TemplateRenderer`, add tests in `TemplateRendererTest`, document it in `docs/event-payload-design.md`, and add a typed method to `NotificationSender` in `../demo`. The envelope stays stable; additive changes bump the minor `schemaVersion`.
- Keep constructor injection and `@ConfigurationProperties`/`@Value` for settings; no secrets in `application.yaml`.
- Known gaps: DLT messages still carry the code; no HMAC address hash or TTL index on `notification_log`; no circuit breaker; Kafka TLS/SASL not configured.
